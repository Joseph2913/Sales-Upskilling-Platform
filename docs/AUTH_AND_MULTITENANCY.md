# Auth & Multi-Tenancy

## Authentication

### Provider
Supabase Auth with OAuth providers: Google and Microsoft. No email/password auth — OAuth only.

### Flow
1. User lands on `/login` → `AuthModal` renders Google + Microsoft sign-in buttons
2. OAuth redirect → Supabase creates/updates `auth.users` record
3. App checks for `profiles` record → creates one if first login
4. App checks for `org_memberships` → if none, redirects to org join flow
5. If user has org membership, loads `OrgContext` and proceeds to `/app/dashboard`

### Join Flow
Users join an organisation via one of three enrollment channels:
- **Invite link:** `/join/:slug` — user clicks link, authenticates, auto-joins the org
- **Join code:** 6-digit code entered in the app after authentication
- **Domain auto-enroll:** If user's email domain matches an org's domain and `auto_enroll` is true, they're automatically added on first login

### Session Management
Supabase handles session persistence via `supabase.auth.onAuthStateChange()`. Tokens refresh automatically. `AuthContext` exposes: `user`, `session`, `loading`, `signIn()`, `signOut()`.

## Role Hierarchy

### Platform-Level Roles (stored in profiles or a separate admin table)
| Role | Access |
|------|--------|
| `super_admin` | Full platform access, can manage all orgs |
| `oxygy_admin` | Can manage all client orgs, view cross-org analytics |

### Org-Level Roles (stored in org_memberships)
| Role | Access |
|------|--------|
| `admin` | Manage org settings, users, enrollment, view org analytics |
| `facilitator` | View learner progress, review submissions, manage cohorts |
| `learner` | Access learning content, tools, artefacts |

## Auth Guards

### AppAuthGuard
Wraps `/app/*`. Checks `AuthContext.session` exists. If not → redirect to `/login`.

### OrgCheckGuard
Wraps `/app/*` (inside AppAuthGuard). Checks user has an active `org_membership`. If not → redirect to org join flow.

### AdminAuthGuard
Wraps `/admin/*`. Checks user has `oxygy_admin` or `super_admin` role. If not → redirect to `/app/dashboard` with toast "Access denied."

## Multi-Tenancy

### Organisation Model
Each client company is an `organisation`. Organisations control:
- **Objective access:** Which of the 6 objectives their users can see (`objective_access` array)
- **Branding:** Custom logo, programme name, primary colour, welcome message
- **Tier:** `foundation` (basic), `accelerator` (mid), `catalyst` (full) — affects feature access
- **User cap:** `max_users` license limit
- **Enrollment:** Multiple channels (links, codes, domain) with usage tracking and expiry

### Data Scoping
All learner data (progress, artefacts, submissions, conversations) is scoped to the user. Org admins see aggregated data for their org only via RLS policies that join through `org_memberships`.

### Org Context
`OrgContext` provides: `currentOrg`, `membership`, `branding`, `objectiveAccess`, `tier`. Components check `objectiveAccess` before rendering objective-related content.

### Branding Application
- Org logo: displayed in sidebar header and top bar
- Programme name: replaces default platform name in nav and page titles
- Primary colour: optionally overrides teal accent for the org's instance (future feature)
- Welcome message: shown on first login after enrollment

## Enrollment Channels

### Link
- Generated by org admin: `/join/acme-sales-2026`
- Unique slug per channel
- Tracks `uses_count` vs `max_uses`
- Optional `expires_at`
- User clicks → authenticates → auto-joins org as learner

### Code
- 6-digit alphanumeric code (e.g., `X7K2M9`)
- User authenticates → enters code in app → joins org
- Same tracking: `uses_count`, `max_uses`, `expires_at`

### Domain
- Org sets domain (e.g., `acme.com`)
- Any user authenticating with `@acme.com` email is auto-enrolled
- `auto_enroll: true` required
- No usage cap by default

### Cohort Assignment
Enrollment channels can optionally assign users to a specific cohort. Cohorts group learners for team views, leaderboards, and facilitator management.
